# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 36-37) | Off-by-one in grace period check: `minutes > 10` returns 0 for a 10-minute-and-1-second punch-in because integer division truncates 601 seconds to 10 minutes (`10 > 10` evaluates to False). | Input punch-in at 09:40:01 for a 09:30 shift returns `0` instead of `10`. | Changed condition to check elapsed seconds strictly greater than 600 (`diff_seconds > 600`), and take floor minutes `int(diff_seconds // 60)` elapsed from shift start. |
| 2 | `compute_late_minutes` (lines 33-37) | Naive timezone replacement: `punch_in.replace(hour=h, minute=m)` assumes `punch_in` is in IST. If `punch_in` is in UTC, replacing hours directly skews the reference time by 5 hours 30 minutes. | Punch-in at 09:35 IST stored as 04:05 UTC produces unexpected negative or zero late minutes. | Converted `punch_in` to IST (`UTC+05:30`) before constructing the shift start instant. |
| 3 | `compute_late_minutes` (lines 33-37) | Broken overnight shift reference: If an overnight shift runs 22:00 to 06:00 and an employee punches in at 00:30, `punch_in.replace(hour=22)` sets the shift start in the future on the current day. | Punching in at 00:30 for a 22:00 shift results in negative seconds and 0 late minutes. | Aligned shift start to the attendance calendar date (the day the shift started, per R1). |
| 4 | `compute_work_hours` (line 41) | Python `round()` uses round-to-even (banker's rounding) instead of standard half-up rounding required by R4. | Work duration of 2.525 hours rounds down to `2.52` instead of `2.53`. | Replaced with `Decimal.quantize(Decimal('0.01'), rounding=ROUND_HALF_UP)`. |
| 5 | `compute_overtime` (line 47) | Minimum overtime threshold ignored: `max(0, int(... / 60))` returns overtime for 1 to 29 minutes, violating R3 (minimum 30 minutes required). | Punching out 15 minutes after shift end returns `15` instead of `0`. | Only return overtime minutes if `overtime_minutes >= 30`, otherwise `0`. |
| 6 | `compute_overtime` (lines 45-46) | Overnight shift end date calculation: `end` is created using `date_str` directly. For overnight shifts, shift end is on the next calendar day. | Overnight shift ending at 06:00 on the next day calculates overtime against 06:00 on the start date, giving ~24 hours of overtime. | Added 1 day to `end` whenever `shift_end <= shift_start`. |
| 7 | `compute_overtime` (lines 46-47) | Offset-naive vs offset-aware datetime subtraction error: `end` has `tzinfo=IST` but `punch_out` may be naive UTC. | Calling `punch_out - end` raises `TypeError: can't subtract offset-naive and offset-aware datetimes`. | Normalized both datetimes to timezone-aware IST before subtraction. |
| 8 | `/health` (lines 72-74) | Fake health check: Returns `{"status": "ok"}` unconditionally without checking if MongoDB is alive. | When MongoDB is offline or unreachable, `/health` still returns 200 instead of 503. | Added `client.admin.command('ping')` inside a try-except block, returning 503 when ping fails. |
| 9 | `create_employee` (lines 79-84) | Race condition on `emp_code`: Relies on check-then-insert (`find_one` followed by `insert_one`) without database unique constraints. | Concurrent duplicate employee creations can both pass `find_one` and create duplicate codes. | Created a unique index on `emp_code` at startup and handle `DuplicateKeyError` to return 409. |
| 10 | `create_employee` (lines 53-61) | Missing schema validations: Allows `shift_start == shift_end` (disallowed by contract), missing regex constraints on `emp_code` (`^EMP\d{4,6}$`) and email. | Submitting `shift_start: "09:00"` and `shift_end: "09:00"` passes with 201 instead of 422. | Added Pydantic field validators and regex patterns matching `openapi.yaml`. |
| 11 | `create_employee` (line 82) | Server creation time format: `datetime.now()` stores local naive time in Mongo, and returns it as a string or datetime rather than epoch milliseconds. | Client receives datetime string/object instead of an integer count of epoch milliseconds. | Stored UTC BSON datetime truncated to seconds and serialized as epoch milliseconds integer. |
| 12 | `list_employees` (line 93) | Off-by-one pagination bug: `skip = page * page_size` skips the first page entirely when `page=1`. | Requesting `page=1, page_size=20` skips the first 20 records. | Changed skip calculation to `(page - 1) * page_size`. |
| 13 | `list_employees` (line 94) | Unfiltered total count: `db.employees.count_documents({})` counts all documents ignoring the `department` filter. | Filtering by department returns `total` for the whole company rather than the filtered count. | Passed the filter query `q` into `count_documents(q)`. |
| 14 | `list_employees` (line 95) | Missing sort order: Results are returned in arbitrary natural order instead of sorted by `emp_code` ascending. | Consecutive queries return differently ordered lists depending on database insertion order. | Added `.sort("emp_code", 1)` to the query cursor. |
| 15 | `punch_in` (lines 101-113) | Unhandled 500 error on unknown employee: When `emp` is None, `emp["shift_start"]` raises an unhandled `TypeError`. | Punching in with a non-existent `emp_code` returns HTTP 500 instead of 404. | Verified employee existence and raised `HTTPException(404, "Employee not found")`. |
| 16 | `punch_in` (lines 104-118) | Check-then-insert race condition: Concurrent punch-ins for the same employee and date can both pass `find_one` and insert duplicate documents. | Simultaneous punch-in requests both return 201 or create duplicate logs. | Created a compound unique index on `(emp_code, date)` and caught `DuplicateKeyError` to return 409. |
| 17 | `punch_in` (lines 102-103) | Incorrect attendance date for overnight shifts: Uses `ts.date().isoformat()` which fails R1 for punch-ins after midnight on overnight shifts. | Punching in at 00:15 for a 22:00-06:00 shift assigns the record to the current day instead of the previous day. | Implemented R1 overnight shift logic to shift date back 1 day when `dt.time() < shift_end`. |
| 18 | `punch_in` & `list_attendance` (lines 119, 149) | Invalid `id` field in response: Injects `doc["id"] = str(...)` which violates the `AttendanceRecord` schema. | Response payload fails OpenAPI schema validation due to unwanted `id` property. | Removed `id` field and returned only schema-compliant fields. |
| 19 | `list_attendance` (lines 144-147) | Massive memory exhaustion / full collection load: `docs = list(db.attendance_logs.find(q))` loads all records into Python memory and sorts in Python. | On a dataset of ~100k records, the endpoint causes high latency, OOM crashes, and timeouts. | Delegated sorting and pagination to MongoDB using indexed `.sort([("date", -1), ("emp_code", 1)]).skip(...).limit(...)`. |
| 20 | `list_attendance` (lines 127-142) | Missing date range validation: Does not check whether `date_from > date_to`. | Passing `date_from=2026-07-10` and `date_to=2026-07-01` returns empty items with 200 instead of 422. | Added validation raising 422 if `date_from > date_to`. |
| 21 | Startup initialization | Missing index setup: Database starts with only default `_id` index, leaving queries unindexed and unique constraints unenforced. | Explain endpoint detects `COLLSCAN` and concurrent requests allow duplicate keys. | Implemented startup lifespan hook creating all required unique and compound indexes idempotently. |

### What was examined and decided was NOT a defect:
- **`os.getenv("MONGO_URI", "mongodb://localhost:27017")` and `MONGO_DB` default fallbacks:** Providing reasonable defaults while allowing real environment variables to override is standard practice and aligns with the environment contract.
- **Exclusion of `_id` from API responses:** Omitting `_id` in responses (`_id: 0` or popping `_id`) is strictly required by the contract since `_id` is an internal MongoDB implementation detail.
- **Absence of user authentication/token parsing:** The assignment specification explicitly states there is no authentication in this exercise and user identifiers like `regularized_by` are passed as plain strings.
